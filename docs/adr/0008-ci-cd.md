# ADR 0008 : intégration et déploiement continus

Statut : accepté le 2026-10-19.

## Contexte

Exigences N1 à N4 et critères R5 et R6. Comptes disponibles : GitHub (dépôt public), Firebase et Vercel. Aucun push ni déploiement sans ton accord explicite.

## Options

| Déploiement | Pour | Contre |
|---|---|---|
| A. Intégration Git de Vercel (production sur `main`, prévisualisation sur chaque PR), plus une protection de branche sur `main` qui exige une CI verte | Aucun jeton Vercel dans GitHub ; prévisualisations gratuites | N4 repose sur la protection de branche |
| B. Déploiement par la CLI Vercel depuis GitHub Actions, après la CI | N4 strict | Un jeton Vercel de plus en secret GitHub |

## Choix

**CI sur GitHub Actions**, quatre jobs :
1. Qualité : ESLint, vérification des types, contrôle de structure (ADR 0009).
2. Tests : Vitest (unitaires et serveur), règles et routes contre les émulateurs Firestore et Auth. Java est installé avec un JDK 21 Temurin. La documentation officielle demande un JDK 11 ou plus ; le JDK 21 couvre aussi les versions récentes de la CLI.
3. Bac à sable : Playwright avec Chromium.
4. Secrets : gitleaks en binaire, en version fixée à l'étape 5. S'y ajoutent la détection de secrets et la protection au push de GitHub, que tu actives dans les réglages du dépôt.

**Déploiement** : option A, plus un job GitHub Actions qui déploie les règles et les index Firestore après une CI verte sur `main`. Ce job s'authentifie avec un compte de service, via `GOOGLE_APPLICATION_CREDENTIALS`. `firebase login:ci` est déprécié.

## Raisons

- Le flux par PR est le cœur de la CI/CD agentique (Q3) : j'ouvre la PR, la CI tourne, et ta validation de la fusion vaut accord de déploiement.
- On a moins de secrets à gérer qu'avec B.

## Secrets (jamais dans le dépôt ni dans le chat ; c'est toi qui les saisis)

| Où | Nom | Contenu |
|---|---|---|
| Vercel | `FIREBASE_SERVICE_ACCOUNT` | Compte de service d'exécution (lecture et écriture Firestore), en base64 |
| Vercel | `KEY_ENCRYPTION_KEY` | Clé maîtresse (ADR 0004) |
| Vercel | `NEXT_PUBLIC_FIREBASE_*` | Configuration client, publique |
| GitHub | `FIREBASE_DEPLOY_SERVICE_ACCOUNT` | Compte de service de déploiement, limité aux règles et aux index |

Les rôles exacts du principe du moindre privilège sont à vérifier à la création des comptes de service.

## Conséquences

- La protection de branche est un réglage du dépôt. Le 2026-10-19, tu m'as autorisé à configurer la CI/CD avec `gh` (protection de branche, workflows). Chaque push, y compris le premier, reste soumis à ton accord explicite.
- Les règles se déploient après le front. Tout changement de règles doit donc rester compatible avec la version précédente.
- La revue IA des PR est prévue en T2 (Q3).

## Amendement du 2026-10-19 : tests navigateur et de bout en bout (T7, T8)

- **Job `sandbox`.** Il installe Chromium, Firefox et WebKit avec Playwright. Il lance les tests du bac à sable en vrai navigateur (mode navigateur de Vitest), puis les tests de bout en bout (Playwright Test) sur un build de production.
- **Pages de test.** Les pages réservées aux tests de bout en bout portent l'extension `.e2e.tsx`. Elles ne sont compilées qu'avec `KATAI_E2E=1`, dans un dossier séparé (`.next-e2e`). Le build normal et Vercel ne les contiennent jamais, et un test unitaire vérifie la configuration.
- **Branche protégée.** `sandbox` rejoint les vérifications obligatoires de `main` dès son premier passage sur une PR.

## Amendement du 2026-10-20 : fournisseur « écho » pour les tests de bout en bout (T15)

- **Ce qu'il fait.** Pour tester tout le parcours d'un essai sans appeler Anthropic, le build de bout en bout active un fournisseur « écho ». Il renvoie le bloc de code écrit dans la spécification, comme un modèle qui la suivrait à la lettre. Le parcours devient ainsi déterministe et gratuit.
- **Conditions d'activation, toutes requises :**
  - `KATAI_FAKE_PROVIDER=1` ;
  - les émulateurs Firebase (`FIREBASE_AUTH_EMULATOR_HOST`) ;
  - aucune variable `VERCEL_ENV`.

  Sur Vercel, les émulateurs sont de toute façon refusés par le garde-fou du SDK Admin (ADR 0003). Un test unitaire vérifie ces conditions.
- **Ce qu'il ne remplace pas.** L'adaptateur Anthropic reste testé à part (SDK réel, `fetch` simulé), et vérifié en réel avec `npm run smoke:provider`.

## Amendement du 2026-10-20 : déploiement des règles et des index, comptes de service (T21)

- **Job `deploy-firestore`.**
  - Quand il tourne : uniquement sur un push vers `main`, après les quatre vérifications, et seulement une fois la variable `FIREBASE_PROJECT_ID` définie. Il reste donc inactif tant que le projet réel n'existe pas.
  - Ce qu'il fait : il déploie `firestore:rules` et `firestore:indexes`, sans rien d'autre, en mode non interactif. La CLI ne supprime jamais un index absent du fichier.
  - La clé : elle est écrite dans un fichier temporaire (droits 600), toujours supprimé à la fin.
  - Un test unitaire lit le workflow et vérifie ces propriétés. Il vérifie aussi que seul ce job lit un secret, et que chaque action est figée par SHA.
- **Environnement GitHub `production`.** Il est limité aux branches protégées, c'est-à-dire `main`. Le secret `FIREBASE_DEPLOY_SERVICE_ACCOUNT` y est rangé : une PR ne peut pas le lire, même en modifiant le workflow.
- **Rôles, vérifiés le 2026-10-20** dans la documentation IAM de Google Cloud et dans le code de `firebase-tools` 15.34.0. La commande `deploy` exige `firebase.projects.get`, plus les permissions de chaque cible.

  | Compte | Rôles |
  |---|---|
  | `katai-runtime` (Vercel, SDK Admin) | Cloud Datastore User ; Firebase Authentication Viewer. Ce dernier donne `firebaseauth.users.get`, nécessaire à `verifyIdToken` avec `checkRevoked` |
  | `katai-deploy` (GitHub) | Firebase Rules Admin ; Cloud Datastore Index Admin ; Service Usage Consumer, pour vérifier que l'API est active ; un rôle personnalisé limité à `firebase.projects.get` |

  Aucun rôle prédéfini ne donne `firebase.projects.get` sans ouvrir aussi d'autres données, comme les comptes utilisateurs ou les données Firestore. D'où le rôle personnalisé. Le premier déploiement confirme la liste : en cas de manque, la CLI nomme la permission absente.
- **Clés de compte de service plutôt que fédération d'identité.**
  - La fédération (Workload Identity Federation) éviterait une clé de longue durée dans GitHub, mais sa mise en place est plus lourde.
  - Le risque d'une clé est contenu : le compte ne peut que publier des règles et des index, la clé ne sort pas de l'environnement `production`, et sa rotation est décrite dans `docs/production.md`.
  - On passera à la fédération si une règle d'organisation interdit les clés, ou dès qu'un compte aura plus de droits.
- **Variables Vercel en Production uniquement.** Les aperçus de PR ne reçoivent ni la configuration Firebase ni les secrets : ils affichent « connexion indisponible » et ne touchent jamais aux données réelles. Les parcours complets restent testés en CI, sur les émulateurs.
- **Région.** Firestore est en `europe-west9` (Paris). La région des fonctions Vercel est réglée sur Paris (`cdg1`) si l'offre le permet, pour rester près de la base.
- **Guide.** `docs/production.md` décrit chaque réglage fait par le porteur du projet, y compris la restriction de la clé d'API du navigateur (domaines autorisés et API utiles).
